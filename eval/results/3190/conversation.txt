#### 🐛 Potential bugs

1. **`Math.floor(stateMaxAge / 1_000)` can round a sub-second TTL to `0`** — `src/modules/auth/oidc/routes/oidc-auth.controller.ts:110`. If `auth.stateTtlMs` is ever configured below `1000`, the OIDC state cookie is written with `maxAge: 0` and is effectively unset, breaking the `state` check in the callback. Today's defaults make this unlikely, but it's an easy footgun. Prefer `Math.max(1, Math.ceil(stateMaxAge / 1_000))` and consider asserting the lower bound at startup. [Fix this →](https://claude.ai/code?q=On%20branch%20feat%2Ffastify%2C%20in%20src%2Fmodules%2Fauth%2Foidc%2Froutes%2Foidc-auth.controller.ts%20line%20110%2C%20replace%20Math.floor(stateMaxAge%20%2F%201_000)%20with%20Math.max(1%2C%20Math.ceil(stateMaxAge%20%2F%201_000))%20so%20sub-second%20stateTtlMs%20values%20don%27t%20zero%20out%20the%20cookie.&repo=safe-global/safe-client-gateway)

2. **`parseBodyLimit` is stricter than the old `bytes` parser it replaces** — `src/app.provider.ts:38-56`. The previous Express config used `body-parser` which delegates to the `bytes` library and accepts e.g. `tb`, `pb`, and looser whitespace/casing rules. The new regex only matches `b|kb|mb|gb` and `\d+(?:\.\d+)?`. A previously valid `EXPRESS_JSON_LIMIT=1tb` (or `'1 KiB'`) now throws at bootstrap. Worth either:
   - documenting the supported units in the env-var docstring at `src/config/entities/configuration.ts:386`, **and/or**
   - reusing the `bytes` package (already a transitive dep) to preserve compatibility.

3. **`NotFoundLoggerMiddleware` types the request as raw `IncomingMessage`** — `src/middleware/not-found-logger.middleware.ts:25`. This works because `@fastify/middie` (used by NestJS' Fastify middleware adapter) does set `originalUrl`, but it isn't part of the Node type. Type drift may make a future change silently fall back to `req.url`. Consider importing the shared `RequestLike` from `http-request.utils.ts` for consistency.

4. **`createTestApplication` skips production-equivalent adapter config** — `src/__tests__/test-app.provider.ts:18`. It calls `new FastifyAdapter()` with no `trustProxy`/`bodyLimit`, while `TestAppProvider.provide()` correctly uses `createFastifyAdapter(configurationService)`. Tests that exercise either should standardize on the configured adapter, otherwise behaviour-drift between integration tests and production is invisible.

#### 🔐 Security / robustness

5. **`getRouteUrl` silently falls back to `'localhost'`** — `src/routes/common/http/http-request.utils.ts:69-74`. If the `Host` header is missing (unusual but possible from internal probes), pagination cursors and any audit logs that include this URL will contain a misleading authority. Previously Express would throw because `request.get('Host')` returned `undefined` and the URL constructor failed. Recommend throwing here too, or at minimum logging a warning, to surface misconfigured callers rather than masking them.

6. **`TenderlySignatureGuard` HMAC over re-stringified body** — `src/modules/alerts/routes/guards/tenderly-signature.guard.ts:57` (pre-existing, but now even more relevant under Fastify). Re-serializing the parsed JSON to compute the HMAC depends on Fastify's parser preserving the exact byte representation that the sender signed. Insertion-order is preserved by `secure-json-parse`, but whitespace, number formatting, and Unicode escapes are not guaranteed. Long-term, prefer Fastify's `rawBody` / a `preParsing` hook to verify against the actual received bytes.

#### 🧪 Test coverage

11. **`@Res({ passthrough: true })` + `Promise<void>` handlers** (e.g. `auth.controller.ts:127`, `oidc-auth.controller.ts:94`) — under Fastify, NestJS will auto-send `undefined`. Behaviour is fine, but a quick e2e check that `POST /v1/auth/verify` returns `200 ""` (not `204`) is worth confirming during smoke testing.

- The `createFastifyAdapterFromConfiguration` split keeping adapter creation pure & testable is the right call given Fastify's construction-time config requirement.
- `RequestLike` abstraction in `http-request.utils.ts` is a nice insulation layer — guards/decorators/filters look largely portable now.

Nothing here is blocking on its own; #1 and #2 are the two I'd want addressed (or explicitly accepted) before merging.
