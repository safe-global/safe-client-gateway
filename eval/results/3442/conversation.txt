Overall this is a clean, well-motivated fix. The coupling of the probe cap to the reopen threshold is elegant — one round of probes is always enough to reach a verdict either way, and no new knob to drift. Slot bookkeeping is symmetric (success and failure both release), and both transitions (`transitionToHalfOpen`, `transitionToOpen`) zero the counter so a subsequent window starts clean. Test coverage exercises the cap, both release paths, the reopen reset, and lazy registration.

A few things worth considering:

### 1. Warn-level log on every rejected HALF_OPEN request — spam risk during the exact scenario this PR addresses
`src/datasources/circuit-breaker/circuit-breaker.service.ts:228-235` logs at `warn` per rejected request. In the outage this cap is meant to survive (hanging upstream, many concurrent callers), the number of rejections per HALF_OPEN window can be large × pods × seconds. Consider `debug`, or a rate-limited/coalesced warn (e.g. only once per HALF_OPEN entry). Not blocking, but the OPEN-state rejection logs at `warn` too and together they may dominate logs during an incident.

### 2. Late `recordSuccess` from a prior HALF_OPEN window can release a slot in a new window
Scenario: circuit was HALF_OPEN → OPEN → (after `timeout`) → HALF_OPEN again. If a probe from the earlier window finally returns and calls `recordSuccess`, `state === HALF_OPEN` is true, so `releaseHalfOpenProbe` decrements a slot that belongs to a *new* probe. `Math.max(0, …)` protects against negatives but does not prevent an extra admission (the freed slot can be handed to another caller). In production this requires ≥ 30 s between windows, so unlikely with the default 30 s HTTP timeout — but the two are equal, so it's not impossible. A per-probe token returned from `canProceed`/`canProceedOrFail` and consumed by `recordSuccess`/`recordFailure` would make this robust; the current coarse counter is what the PR intentionally uses. Worth acknowledging in a comment on `releaseHalfOpenProbe`, or accepting as a documented trade-off.

### 3. Close-threshold vs probe cap creates a slow close under defaults
With defaults `threshold=10`, `halfOpenFailureRateThreshold=30` → probe cap 3, but consecutive successes to close = 10. So HALF_OPEN needs ~4 sequential rounds of admitted probes to close. This is a design choice, not a bug, but users tuning `halfOpenFailureRateThreshold` down (to make reopen more aggressive) also shrink the probe cap proportionally and lengthen close time. The `configuration.ts` comment mentions the cap coupling but not the close-time consequence — a line there would prevent surprise.

### 4. `getEffectiveFailureThreshold` now has two meanings
`src/datasources/circuit-breaker/circuit-breaker.service.ts:220` uses it as `maxInFlight`, while `recordFailure` uses it as the reopen threshold. The reader has to know they're intentionally equal. A one-liner in the method's JSDoc — "In HALF_OPEN this doubles as the concurrent-probe cap" — makes the coupling explicit without changing behaviour.

### 5. Nit: test-module-scope circuit name
`circuit-breaker.service.spec.ts:15` — `const circuitName = faker.string.alphanumeric()` at module scope defaults to length 1 and is shared across every `it`. Faker is seeded so it's deterministic, but a 1-char name is fragile if a future test adds an explicit `'a'`/`'b'` circuit. Consider `faker.string.alphanumeric({ length: 10 })` or inline names.

### Positives
- Removing the explicit `getOrRegisterCircuit` from `network.module.ts` and moving registration lazy inside `recordFailure` is the right simplification.
- `transitionToOpen` zeroing `halfOpenInFlight` (l. 461) closes the obvious leak from the previous design.
- The `Discard old failures` handling correctly skips in HALF_OPEN by branching before `discardOldFailures` — that avoids double-counting the transition reset.

Nothing here blocks merging; the two most useful follow-ups are the log-level question (#1) and a short comment acknowledging the late-slot-release edge (#2).
