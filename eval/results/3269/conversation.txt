Focused review of what could be improved. Nice work on the util, the wire-format transforms, and the unit coverage for `BillingService`.

#### Security

1. **`GET /v1/billing/sessions/:sessionId` has no ownership check** — [`billing.controller.ts:177-182`](src/modules/billing/routes/billing.controller.ts#L177) and [`billing.service.ts:98-102`](src/modules/billing/routes/billing.service.ts#L98). The route is protected by `AuthGuard`, but any authenticated user can fetch any session by ID and receive `amountTotal`, `customer`, `subscription`, `invoice`, and `metadata`. Session IDs are opaque but effectively guessable across users. Consider requiring the caller to be a member of the space referenced by `client_reference_id`/`customer`, or resolving the session through a space-scoped route like `GET /v1/billing/spaces/:spaceId/sessions/:sessionId`.

2. **Open-redirect surface via `returnUrl`** — [`billing.controller.ts:37`](src/modules/billing/routes/billing.controller.ts#L37). `ReturnUrlSchema = z.url()` accepts any well-formed absolute URL, including attacker-controlled origins. Since the value is embedded in Stripe hosted flows and served back to users, it's a classic open-redirect vector. Restrict to an allowlist of trusted origins (e.g. the wallet-web hosts) rather than any URL.

#### Correctness

3. **De-dup precedence in `getSpacePaymentLinks` is inverted** — [`billing.service.ts:69-80`](src/modules/billing/routes/billing.service.ts#L69). `new Map([...spaceLinks, ...generalLinks].map((l) => [l.id, l]))` lets later entries overwrite earlier ones, so a duplicate ID keeps the **general** link and discards the **space-specific** one. If a payment link ever differs (metadata/pricing overrides for the space), the space version is silently dropped. Either put `generalLinks` first, or explicitly prefer the space entry. The existing test only asserts count (identical objects), so it doesn't catch this.

#### Code quality

4. **Double `@Param('spaceId', ...)` is repeated 4×** — [`billing.controller.ts:68-69,105-106,131-132,159-160`](src/modules/billing/routes/billing.controller.ts#L68). Reading the same route param twice — once with `SpaceIdPipe` for the numeric id, once raw for the UUID — is subtle and easy to break on a future rename. A small custom decorator/pipe that returns `{ id, uuid }` (or the whole `Space`) would remove the duplication and shave one DB round-trip. Right now every space-scoped billing call runs `findIdByUuid` (pipe) + `membersRepository.findOne` (assertSpaceMember) before touching the billing API.

5. **No format validation on `planId` / `paymentLinkId` / `sessionId`** — [`billing.controller.ts:89,161,179`](src/modules/billing/routes/billing.controller.ts#L89). These are interpolated verbatim into `${baseUri}/api/v1/…/${id}` in `billing-api.service.ts`. Unvalidated user input in path segments is a mild footgun (encoded slashes, weird chars). Wrapping with a small `ValidationPipe(z.string().regex(...))` would harden the client.

#### Tests

6. **No controller/e2e coverage for the new endpoints** — only `billing.service.spec.ts` was added. Guard application (`AuthGuard` on each new route), 400 on invalid UUID via `SpaceIdPipe`, 401/403 paths, and `returnUrl` validation aren't exercised at HTTP level. The pattern from `billing-webhook-auth.guard.integration.spec.ts` would fit. Adding at least one integration test per new route would catch decorator/guard regressions the unit tests can't.

7. **De-dup test doesn't verify precedence** — [`billing.service.spec.ts:184-199`](src/modules/billing/routes/billing.service.spec.ts#L184). Uses the same object in both lists; would still pass under either precedence. Use two objects with the same `id` and different `active`/`metadata` to lock behavior.
