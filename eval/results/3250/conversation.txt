### Review

Solid, well-scoped change. The fail-open semantics match the existing read-side filter, tests cover the three interesting branches (persists / rejects / fail-open), and the DI wiring is clean. A few small suggestions:

**1. Duplicate logic across the two services** — `assertNoneDeployed` in `counterfactual-safes.service.ts:80-101` and `filterUndeployed` in `space-counterfactual-safes.service.ts:60-77` implement essentially the same primitive: "map over Safes → parallel `isSafe` → fail open on error". Consider extracting a shared helper (e.g. `checkDeployment(safes, safeRepository): Promise<Array<boolean>>`) so future changes to the fail-open policy or error logging live in one place.

**2. Silent fail-open swallows all errors** — `counterfactual-safes.service.ts:90-92` and `space-counterfactual-safes.service.ts:70-72` both `catch {}` without any logging. If the transaction service is down or returning malformed data, this endpoint will silently continue and you lose observability into a state where the guard is effectively disabled. Recommend injecting `LoggingService` and logging at `warn` level (chainId + address + error) so ops has a signal when the check is degraded.

**3. Duplicate `isSafe` calls for repeated addresses** — If a batched POST includes the same `(chainId, address)` twice (e.g. accidental client dupe), `isSafe` is invoked once per occurrence. Minor, but a `new Map()` dedupe by `${chainId}:${address}` in `assertNoneDeployed` would avoid redundant tx-service requests. Same applies to `filterUndeployed` if the underlying repository can return duplicates.

**4. Response-type invariant in `space-counterfactual-safes.service.ts`** — After filtering, a chain whose Safes were all deployed will be missing from the response `safes` object. The tests only assert on non-empty chains — worth double-checking clients don't rely on an empty array being present per chain. If they might, `transformCounterfactualSafesResponse` may need to preserve empty buckets.

**5. Test — DTO builder duplicates the mapping in the service** — `counterfactual-safes.service.spec.ts:22-40` re-implements the field-mapping already done in `CounterfactualSafesService.create` (`to → setupTo`, `data → setupData`, etc.). Consider a small `createCounterfactualSafeDtoBuilder()` in the domain builders so the DTO shape is asserted in one place and tests don't drift when the DTO changes.

**6. Small nit — comment style** — `counterfactual-safes.service.ts:78-79` and `space-counterfactual-safes.service.ts:51-52` explain the *what* rather than a non-obvious *why*. The "fail open" reasoning is the interesting part; the "reject if any deployed" part is obvious from the code. Consider trimming to just the fail-open rationale.

No blocking issues. Test coverage is proportional to the change.
