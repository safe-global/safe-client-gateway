Nice cleanup — pulling relayer selection out of env vars and into the chain config is a clear improvement, and the new `RelayManager` is much easier to read. A few things worth addressing before merging:

#### 1. Backward-compat fallback removed — rollout risk
`src/modules/relay/domain/relay.manager.ts:50` — the previous code fell back to `DailyLimitRelayer` for any unconfigured chain. Now `null` → `NoRelayerDefinedError` (403). If the config service hasn't been rolled out with `relayerType` populated for every supported chain when CGW deploys, every `POST /v1/chains/:id/relay` call on those chains will start 403'ing. Worth confirming the config-service PR (safe-config-service#1555) ships first **and** is fully populated before this lands. Also worth a unit/integration test asserting the strict-mode behavior on a chain that has historically been "no env config, falls back to daily limit".

#### 2. Schema silently swallows unknown relayer types
`src/modules/chains/domain/entities/schemas/chain.schema.ts:108`
```ts
relayerType: z.enum(RelayerType).nullable().catch(null),
```
`.catch(null)` means any new relayer-type string introduced by the config service (e.g. a future `GTF_V2`) silently becomes `null` here → `NoRelayerDefinedError` → 403, with no log line to explain it. Consider logging in the `.catch` path (use a transform) so this divergence is observable instead of being a silent outage waiting to happen.

#### 3. `RelayerTypeNotImplementedError` returns 403 Forbidden — wrong status
`src/modules/relay/domain/errors/relayer-type-not-implemented.error.ts:3-7` extends `ForbiddenException`. Semantically this is "the server hasn't implemented this yet", not "you're not allowed". `501 Not Implemented` (or `503`) communicates the situation more honestly to clients and to dashboards/alerting. Same applies to `NoRelayerDefinedError` arguably (it's a server config gap, not a permission denial), though 403 is at least less misleading there.

#### 4. Inconsistent error status between fees and relay paths for the same state
- `src/modules/fees/routes/fees.service.ts:24-28` → `BadRequestException` (400) when `relayerType !== RELAY_FEE`.
- `src/modules/relay/domain/relay.manager.ts` → `NoRelayerDefinedError` (403) / `RelayerTypeNotImplementedError` (403).

Both paths represent "chain not configured for this kind of relay" but return different statuses with different messages. Consider unifying so clients can handle a single contract.

#### 5. `getRelaysRemaining` type drift between interface and impl
- `src/modules/relay/domain/interfaces/relayer.interface.ts:51-55` declares `safeTxHash?: Hex` (optional).
- `src/modules/relay/domain/relayers/relay-fee.relayer.ts:121-125` declares `safeTxHash: Hex` (required) and unconditionally forwards it to `feeServiceApi.canRelay`.

The controller (`relay.controller.ts:161-167`) sends it through as optional. A request to a `RELAY_FEE` chain without `safeTxHash` now hits the fee service with `undefined` — previously the `enabledChainIds` guard short-circuited and the chain-mismatch case returned `{ remaining: 0, limit: 0 }`. Either narrow the interface, or add an explicit guard returning `{ remaining: 0, limit: 0 }` when `safeTxHash` is absent.

#### 6. Exception filter applied per-method instead of class-level
`src/modules/relay/routes/relay.controller.ts:79-90` and `:156` register `RelayerNotAvailableExceptionFilter` on each route individually. Both routes that go through `RelayManager.getRelayer` need it; promoting it to `@UseFilters` at the class level removes the chance of forgetting it on a future endpoint.

#### 7. Cache TTL changes the rollout story for relayer config
`chainsRepository.getChain` is cache-backed (`config-api.service.ts:75-82`). Previously, switching a chain's relayer mode required a CGW redeploy; now it requires a config-service update **plus** waiting out the chain cache (or running `clearChain`). Worth either a note in the PR description on operator workflow, or an admin hook to invalidate when relayer config changes.

#### 8. Test helper hard-codes chain partition
`src/modules/relay/routes/relay.controller.integration.spec.ts:80-88` introduces `relayerTypeForChainId` that re-derives the relayer type from `dailyLimitChainIds` / `noFeeCampaignSupportedChainIds` test constants. This is the old env-var partition reimplemented inside the test. Cleaner to set `relayerType` directly on the chain builder per test case — it'd make the routing logic the SUT actually exercises more explicit.

#### Minor
- `relayer-type.entity.ts:9` — `(typeof RelayerType)[keyof typeof RelayerType]` works but a TS `enum` or `as const satisfies Record<string,string>` is the codebase's more usual idiom; not a blocker.
- `RelayerTypeNotImplementedError`'s `relayerType` parameter is typed `string` — narrow to `RelayerType` since callers only pass known enum values.
- The integration test repeats the same `networkService.get.mockImplementation` chain-config stub in four tests — extract to a `mockChain(chain)` helper.

Overall test coverage on the new branching logic looks solid; the main concerns are the **rollout sequencing (#1)**, **silent catch in the schema (#2)**, and **status-code semantics (#3/#4)**.
