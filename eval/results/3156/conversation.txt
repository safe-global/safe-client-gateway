### Claude PR Review

The fix correctly tightens both authorization paths (`assertMember` and `getSpaceAs`) to `ACTIVE`, and the `spaces.service` change properly hides the roster and `safeCount` from pending invitees. Below are the things worth improving.

---

#### 1. Test helper duplication across three e2e specs

`createActiveMember` / `createPendingMember` are now near-verbatim copies in:

- `address-books.controller.e2e-spec.ts:798-846`
- `user-address-book.controller.e2e-spec.ts:458-510`
- `address-book-requests.controller.e2e-spec.ts:521-549`

Same body (invite → mint JWT from returned `userId` → optionally accept). Extract to a shared test util (e.g. `src/modules/spaces/__tests__/helpers/members.ts`) — otherwise the next ACTIVE/INVITED rule change will need to be repeated 3× and will inevitably drift.

#### 2. Inconsistent `accessTokenForUserId` extraction

`user-address-book.controller.e2e-spec.ts:454-457` extracts a tidy `accessTokenForUserId` helper, but `address-books.controller.e2e-spec.ts:830-834` and `address-book-requests.controller.e2e-spec.ts:541-545` inline the same `siweAuthPayloadDtoBuilder().with('sub', …).build()` pattern. Fold them into the shared helper from item 1.

#### 3. `updateAlias` for pending invitee returns 404, not 403

`src/modules/users/domain/members.repository.ts:411` now narrows the WHERE to `status: 'ACTIVE'`. When a pending invitee calls `PATCH /members/alias`, `updateResult.affected === 0` triggers `NotFoundException` ([repository.ts:415-417](https://github.com/safe-global/safe-client-gateway/blob/fix/space-access-require-active-member/src/modules/users/domain/members.repository.ts#L415-L417)). Everywhere else in this PR a pending caller is rejected with `ForbiddenException` (via `assertMember`). For semantic consistency, prefer calling `assertMember` first, then performing the update — that way the rule lives in one place. ([Fix this →](https://claude.ai/code?q=In%20src%2Fmodules%2Fusers%2Fdomain%2Fmembers.repository.ts%20updateAlias%2C%20call%20assertMember%20first%20so%20a%20pending%20invitee%20gets%20403%20rather%20than%20404%2C%20matching%20the%20rest%20of%20the%20PR.&repo=safe-global/safe-client-gateway))

#### 4. JWT `signer_address` ≠ invited address in the helpers

In all three helpers the access token is built from a fresh `siweAuthPayloadDtoBuilder()` that only overrides `sub`. The token's `signer_address` is unrelated to the wallet that was invited. Auth keys on `sub` so it works, but any future test that asserts wallet-derived state via the SIWE payload will silently use the wrong address. A comment on the helper (or reusing `memberAuthPayloadDto` with `sub` overridden) would prevent that footgun.

#### 5. Minor: roster query still fetches all members for pending invitees

`spaces.service.ts:83-100` queries the space with `relations: { members: true, safes: true }` even when the caller is `INVITED`, then filters in JS at `spaces.service.ts:111-113`. Correct, but a pending invitee still triggers a wide read. If a space grows large this could matter — easy follow-up is to skip those relations when `callerIsActive` is false for that space.

#### 6. Swagger description for `safeCount` not updated

`members.controller.ts` got the "pending only sees own row" note, but the spaces list/get endpoints don't mention that pending invitees see `safeCount: 0`. Worth a one-line addition to the `getSpaces` / `getSpace` swagger so clients aren't surprised.
