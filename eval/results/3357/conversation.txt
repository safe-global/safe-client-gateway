Small, focused workflow — pinned SHAs, minimal permissions, sensible fail-open on the automated path. A few things worth tightening.

### Findings

**1. Manual dispatch checks out the wrong ref for a specific version** — `.github/workflows/linear-release.yml:55`

```yaml
ref: ${{ github.event.release.tag_name || github.ref }}
```

On `workflow_dispatch` with `version: 1.100.0`, this checks out whatever branch the run was launched from (typically `main`), not `v1.100.0`. If the action derives its commit range from the checked-out `HEAD` (rather than resolving the tag itself), a backfill for an older release will scan commits from `main`, not from that tag's history. Consider resolving `refs/tags/v${VERSION}` after the version step and checking it out — or verify that the action always resolves versions to tags server-side and never touches the workspace HEAD.

**2. Backfill runs lose the GitHub release link** — `.github/workflows/linear-release.yml:95`

```yaml
links: ${{ github.event.release.html_url }}
```

On `workflow_dispatch`, `github.event.release` is undefined, so `links` is empty and the re-synced Linear release has no link back to the GitHub release. Easy fix: after resolving `VERSION`, look up the release URL and expose it as another step output:

```bash
RELEASE_URL=$(gh api "repos/$REPO/releases/tags/v$VERSION" --jq '.html_url')
echo "url=$RELEASE_URL" >> "$GITHUB_OUTPUT"
```

then pass `links: ${{ steps.version.outputs.url }}` — same value for both triggers.

**3. `dry_run` is empty on the release trigger** — `.github/workflows/linear-release.yml:96`

`inputs.dry_run` isn't set on the `release` event, so this expands to an empty string. It happens to be falsy for most action wrappers, but relying on that is subtle. Prefer an explicit fallback:

```yaml
dry_run: ${{ inputs.dry_run || false }}
```

**4. No format validation on the manual version input** — `.github/workflows/linear-release.yml:65-82`

`VERSION` is only checked for emptiness. A typo like `1.1220` or `v1.122` silently propagates into the Linear API. A cheap semver-ish regex here would make manual runs fail fast rather than at Linear:

```bash
if ! [[ "$VERSION" =~ ^[0-9]+\.[0-9]+\.[0-9]+([.-].+)?$ ]]; then
  echo "::error::Invalid version: $VERSION"; exit 1
fi
```

**5. Concurrency group can collide across distinct backfills** — `.github/workflows/linear-release.yml:39`

```yaml
group: linear-release-${{ github.event.release.tag_name || inputs.version || github.ref }}
```

Two manual dispatches from `main` without `version` both key on `github.ref` (`refs/heads/main`) and serialize even though they resolve to the same version. Not harmful, but the group is more informative if it uses `inputs.version` unconditionally on the manual path (accept the tradeoff that unversioned dispatches don't dedupe against a concurrent release event).

### Non-issues, for context

- SPDX header present, actions pinned by SHA, `permissions: {}` at workflow level with `contents: read` at job level — all good.
- Skipping `yarn format`/`lint`/`test` is fine here (YAML only, no Biome/test coverage).

The job inherits GitHub's 360-minute default. If the Linear action hangs on a network call, a re-run has to wait out that ceiling before it's clear the job is stuck. A conservative cap like `timeout-minutes: 10` would fail a hung sync fast enough to re-run the same day, without truncating a real scan.     runs-on: ubuntu-latest

    permissions:
