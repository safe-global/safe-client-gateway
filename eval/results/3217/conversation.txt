### Correctness / robustness

**1. Public key is only presence-checked at boot** — `src/modules/billing/domain/billing-auth.service.ts:59-61`
`getOrThrow` guards a missing key, but a malformed / truncated PEM (very common with env-var newline mangling) will pass boot and then fail every single webhook. The module already claims to "fail fast at boot" — make that true by attempting `crypto.createPublicKey({ key, format: 'pem' })` in the constructor (or in the config validator, gated on `FF_BILLING_WEBHOOK=true` + production/staging).

**2. `Authorization` header can be `string[]` per Express types** — `src/modules/billing/routes/guards/billing-webhook-auth.guard.ts:40-45`
`request.headers.authorization` is typed `string | string[] | undefined`. If it's ever an array, `header?.startsWith('Bearer ')` throws (arrays have no `startsWith`) — the 500 will bypass the `UnauthorizedException` path. In practice Node collapses the header, but guard against the type contract:
```ts
const header = request.headers.authorization;
if (typeof header !== 'string' || !header.startsWith('Bearer ')) return null;
```

**3. `expiresInDays` is unbounded** — `scripts/generate-token.ts:81-88`
A typo like `--expires-in 18250` mints a ~50-year token that survives the entire key rotation lifecycle. Consider an upper cap (e.g. 10y) and log the resolved value with a warning above some threshold.

**4. `iss === aud` is intentional but worth a hardening pass** — `src/modules/billing/domain/billing-auth.service.ts:79-80`
Documented ("receiver issues the credential"), but this means any other CGW-minted token targeted at itself for a different purpose would satisfy `iss`+`aud`. Layer‑2 (`SERVICE_ACCESS` role/markers) is what actually prevents crossover — fine, but worth an inline comment on `verify()` making that dependency explicit.

---

### Structure / maintainability

**5. `scripts/generate-token.ts:main()` handles two signing modes in one 60-line function.**
Split into `mintViaKms(claimsArgs, kms)` and `mintLocally(claimsArgs, config)`; keep `main` doing arg parsing + orchestration + printing. (Also raised inline by PooyaRaki.)

**6. `KmsSignerConfig`, `IKmsSigner`, and `resolveCredentials` live in two files.** — `src/datasources/kms/aws-kms-signer.service.ts:11-22`
Move the interface + config type + helper into `kms-signer.interface.ts` (or a dedicated `kms-signer.types.ts`) so the service file is only the implementation.

**7. `BillingAuthService` mixes DI-instance responsibilities (verify) with static factory methods (`mint`, `mintViaSigner`).**
Works, but the static methods have nothing to do with the injected service — they only exist here because they share `buildClaims`. Extracting `BillingTokenMinter` (pure module, used by the CLI) from `BillingAuthService` (Nest-injected verifier) would remove the CLI's dependency on the DI-decorated class and make the "app never signs" boundary structural rather than by convention.
