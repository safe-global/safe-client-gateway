#### Design / boundaries

1. **`IBillingApi.clearSubscriptions` leaks cache into the domain interface** — `src/domain/interfaces/billing-api.interface.ts:78`. The domain contract now advertises a cache-invalidation method purely so `SubscriptionSyncService` can call it (`subscription-sync.service.ts:268`). That inverts the layer rule: the domain shouldn't know Redis exists. It works today, but the more principled home is a small cache helper next to the datasource (or the pending `BillingRepository`); the webhook path can depend on that directly and `IBillingApi` goes back to describing upstream shape only. Worth folding into the same follow-up as the `Raw<T>` conversion so it doesn't ossify.

2. **Preview/PATCH inconsistency around ambiguous prices** — `billing.service.ts:186` deliberately skips link resolution in `previewSubscriptionUpdate` because the upstream keys on price alone, but `updateSubscription` (line 391-402) throws 409 with `"specify which paymentLinkId to use"` in exactly the multi-link case. A client can therefore obtain a quote it can never apply without a follow-up round trip to discover it needs a `paymentLinkId`. Either surface the ambiguity in the preview response (list the candidate links) or reject the preview symmetrically — right now the mismatch is only visible after the PATCH fails.

#### Correctness / small bugs

3. **`findOwnedSubscription` reads *all* statuses to find one id** — `billing.service.ts:343-354`. It fetches every subscription for the customer and `.find(...)`s by id, which is fine for a normal customer but grows linearly with historical (canceled/expired) subscriptions. If the upstream has a `GET /subscriptions/:id` scoped by customer, prefer it. If not, at minimum the "already-cached-under-`all`" cache dir avoids re-hitting the upstream, so the concern is bounded — noting only because the comment implies status doesn't matter, and it does at the payload-size level.

4. **`clearSubscriptions` uses the parent key, relying on `deleteByKey` to drop every filter** — `cache.router.ts:1229` + `billing-api.service.ts:301`. The comment "*the subscription may be listed under any cached filter*" is only true if `deleteByKey` deletes the whole hash (not one field). This holds for the current `ICacheService.deleteByKey`, but the coupling is implicit — a spec or a code comment on `getBillingSubscriptionsCacheKey` making the "drops all fields" contract explicit would keep a future cache refactor from silently leaving stale filters behind.

#### Tests

5. **`billing.service.spec.ts:52-63` — the `billingApiMock` object doesn't declare `clearSubscriptions`**, and the `as MockedObject<IBillingApi>` cast hides it. `BillingService` happens not to call it, but if it ever does (e.g. after the repository conversion), the mock will silently return `undefined` on a `Promise`-returning method — nastier than a clear "method not implemented" failure. Either declare it as `vi.fn()` in the mock or narrow the type to `MockedObject<Pick<IBillingApi, ...actually used methods>>`. The `SubscriptionSyncService` spec already uses the `Pick` pattern for other repositories — same idea.

6. **Elevation coverage of `preview-update` is deliberately absent** — the PR body calls this out and points at 11 sibling GETs in the same state. The rule doesn't require it, but a `TODO(PLA-XXXX)` comment beside the `@UseGuards(AuthGuard)` on `billing.controller.ts:229` would make the follow-up discoverable from the code, not only from the description.

#### Nits

7. **`billing-api.service.ts:266-295` — the `.then(async …).then(parse)` chain** is dense. A straight `const { data } = await this.networkService.patch(...); await this.clearSubscriptions(...).catch(...); return this.parse(Promise.resolve(data), schema);` reads the same intent (cache clears before parse fails) with one less callback level. Style only.

8. **`security.md` doc update lists `patch`** — good; keep an eye on the `patch` example not gaining a body-less variant, because `FetchNetworkService.patch` allows `data?: object` and calls `JSON.stringify(undefined)` → `body: undefined`. Harmless, but not the shape the doc implies.

---

Overall this is a well-scoped, well-tested change with clear reasoning in the code comments, and the trickiest parts (ordering of the "already on plan" check, cache-clear-before-parse, `paymentLinkId` treated as untrusted) are all explicitly justified. The above are quality-of-life items rather than blockers.
