Overall the migration is clean and additive, the pipe split is the right shape, and the legacy fallback is well-isolated and TODO-marked. A few things worth tightening before merge.

### Findings

#### 1. `GET /spaces/:id` does two extra round-trips it doesn't need

`SpacesController.getOne` (`spaces.controller.ts:169-175`) is the only legacy-accepting read endpoint that does **not** use `LegacySpaceIdPipe`. Instead it calls `spacesService.resolveUuid(idOrUuid)` (`spaces.service.ts:125-132`), which:

1. queries `findIdByIdOrUuid` → returns `id`
2. queries `findOneOrFail` → returns `uuid`
3. then `findSpaces(uuid)` runs the members query + spaces query keyed on `space.uuid`

That's **4 DB queries** per `GET /spaces/:id` where the other legacy endpoints do 1+N. Either:
- use `LegacySpaceIdPipe` here too and have `findSpaces` accept `spaceId: number` (keyed on `space.id`), or
- have `findIdByIdOrUuid` return `Pick<Space, 'id' | 'uuid'>` in a single query so the second `findOneOrFail` goes away.

Same code path is the hottest single-space read on the FE, so this is worth fixing.

#### 2. Inconsistent 400 error bodies between the two pipes

- `SpaceIdPipe` → `Validation failed (uuid is expected)` (NestJS `ParseUUIDPipe` default)
- `LegacySpaceIdPipe` → `Invalid space identifier` (custom, thrown from the repository in `findIdByIdOrUuid`)

The PR description says "client error contracts stay stable", but the two pipes return different shapes for the same class of error. Pick one message and use it from both pipes (and ideally throw from the pipe, not the repository — `findIdByIdOrUuid` currently couples the repo to `BadRequestException` / `@nestjs/common`).

#### 3. No tests for the new repository methods or pipes

I couldn't find unit or integration coverage for `findIdByUuid`, `findIdByIdOrUuid`, `SpaceIdPipe`, or `LegacySpaceIdPipe`:

```bash
grep -rn "findIdByUuid\|findIdByIdOrUuid\|LegacySpaceIdPipe" src/ --include="*.spec.ts"
# (no results)
```

At minimum please add cases for:
- valid UUID → resolves to id
- valid numeric → resolves to id (legacy only)
- numeric > `DB_MAX_SAFE_INTEGER` → 400
- malformed string → 400
- valid UUID syntactically but no row → 404
- numeric on `SpaceIdPipe` (write endpoint) → 400 (this guarantee is called out in the PR description but I don't see the e2e test for it on `PATCH /spaces/:id`).

#### 4. Redundant validation in `findIdByIdOrUuid` (`spaces.repository.ts:232-252`)

```ts
if (/^\d+$/.test(value)) { ... }
if (/^[0-9a-f]{8}-[0-9a-f]{4}-...$/i.test(value)) { ... }
```

The UUID regex here doesn't enforce version/variant bits (unlike `ParseUUIDPipe`), so `SpaceIdPipe` and `LegacySpaceIdPipe` accept slightly different UUID sets. Either reuse `ParseUUIDPipe` here too, or pull the predicate into a shared helper so both code paths agree.

#### 5. `acceptInvite` / `declineInvite` are UUID-only

`members.controller.ts:141-153,180-189` apply `SpaceIdPipe` to invite-accept/decline. The PR description does call this out, but: if a previously emailed invite link uses a numeric space id, the user clicking it will hit a 400. If invite emails are already in the wild with numeric IDs, consider keeping these two routes on `LegacySpaceIdPipe` for the deprecation window — the write/read split argument is weaker here since the user is acting on a link, not entering data.

#### 6. Migration `down` is not idempotent

`migrations/1779200000000-add-space-uuid.ts:15-18` uses bare `DROP INDEX` / `DROP COLUMN`. If `up` partially fails (e.g. column added, index creation fails), `down` will then fail on the missing index. `DROP INDEX IF EXISTS` / `DROP COLUMN IF EXISTS` makes the rollback safer. Also worth confirming `gen_random_uuid()` is available without `pgcrypto` (PG ≥ 13 ships it in `pg_catalog`; earlier versions need the extension).

#### 7. Minor

- `spaces.repository.ts:32` carries a pre-existing `// TODO: Add tests` — the new methods extended this gap rather than closing it.
- `Invitation` (`users/domain/entities/invitation.entity.ts`) now types `spaceId: Space['uuid']` (string) but `Invitation` in `routes/entities/invitation.entity.ts` still has `@ApiProperty({ type: Number })` for `userId` — unrelated to this PR but worth a glance while you're in there.
