### Code review

Overall a well-scoped change with careful reasoning in the PR description; the seat-key contract, the lock-before-count sequence, and the guard removal are all defensible and well-tested. A few small things worth considering:

#### 1. `SEAT_KEY` string is interpolated into raw SQL without wrapping the join column

`src/modules/spaces/domain/safes/space-safes.repository.ts:33` defines `const SEAT_KEY = 'COALESCE(safe.address_index, safe.address)'`, hard-coded to the `safe` alias. It is then interpolated in `countNewSeats` at line 270 into a query that also aliases the join `AS safe`, so it works — but there's no compile-time check that any future rewrite (e.g., renaming the alias) will notice. A small comment near `SEAT_KEY` noting "requires the join alias `safe`" would harden this against a rename. Not a bug today.

#### 2. `countNewSeats` sends duplicates through the query unnecessarily

`space-safes.repository.ts:256-258` builds a `Set` of seat keys — good — but the whole set is then converted back to an array and unnested. Since `NOT EXISTS` semantics dedupe naturally, this is fine, but the intermediate `Set(...map(...))` allocation is unneeded once you plan to `unnest` the values; `Array.from(new Set(...))` is a wash. Optional: consider passing the raw array and letting SQL dedupe, or drop the Set — it's just style either way.

#### 3. Docstring for `PreparedSpaceSafe.plaintextAddress` conflicts with usage

`space-safes.repository.interface.ts:19-25` says "Only `insertRows` reads inside it," but `countNewSeats` now also reads `PreparedSpaceSafe` (well, a `Pick<...,'address'|'addressIndex'>` of it — `plaintextAddress` is not read). The docstring is technically still correct for `plaintextAddress`, but the surrounding wording ("Only `insertRows` reads inside it") is now stale for `PreparedSpaceSafe` overall. Consider tightening the wording to reflect the additional consumer, or narrow the type used by `countNewSeats` further.

#### 4. `entitlements.rules.ts:fitsWithinQuota` semantics for `delta: 0`, over-quota space

Confirmed by tests (`entitlements.rules.spec.ts:62-63`) and by `entitlements.service.integration.spec.ts:1269-1277`: a space *over* its quota (e.g. after a downgrade) is still rejected for a `delta: 0` add. The PR description acknowledges this is out of scope for the ticket, but note that in the seat-charging flow this means a downgraded Workspace cannot add a new chain to a Safe it already holds until it removes something. That is likely the desired product behavior — worth double-checking with product before shipping since PLA-1975 spec ("at its seat limit") is ambiguous vs. "over its limit."

#### 5. Broadening `Pick` in `countNewSeats` weakens the type-safety of dedup

`space-safes.repository.interface.ts:101-107` accepts `Pick<PreparedSpaceSafe, 'address' | 'addressIndex'>` — callers can pass any object satisfying that shape (e.g. a caller could pass unencrypted plaintext where a blind index exists). Today only `SpaceSafesService.create` invokes it, but if a future caller forgets to run `encryptRows` first, `addressIndex` will be `null` and the dedup key will be the plaintext, which will not match the encrypted rows already in the table — a silent overcount. Consider requiring the caller to hand over the exact `PreparedSpaceSafe` values, or add an assertion that when encryption is enabled `addressIndex` is not null.

#### 6. Test coverage of the seat-lock concurrency case is good

`space-safes.repository.integration.spec.ts:448-508` proves the lock+count+insert sequence works under concurrency — nice test. One small readability nit: the ad-hoc `addSafeUnderQuota` inline in the spec duplicates the `SpaceSafesService.create` sequence; consider extracting a helper closer to the service to keep the test asserting behavior of shared code rather than a re-implementation of it. Optional.

#### 7. `spaces.service.ts:113-119`: `Promise.all` on a batch that can grow

`countSeatsBySpaceIds` is now called once per listing with all space ids — good, single query. `resolveInvitedByNames` still fans out over wallets/emails. No issue for typical membership sizes, just noting that this is now the tightest place to catch a future N+1 if listings grow.

#### 8. No new migration, per PR description

The PR description carefully justifies not adding an index for the new seat-key filter target, with a measurement on 1M rows. That is the right process (per `database-and-migrations.md`); worth keeping the measurement notes in the commit body or as a follow-up doc so a future reviewer sees why the index rule was deliberately skipped here.
