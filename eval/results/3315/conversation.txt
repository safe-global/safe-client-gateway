### 1. New env vars are missing from `RootConfigurationSchema` (non‑negotiable #7)

`src/config/entities/configuration.ts:61-64` introduces `AUTH_ELEVATION_WINDOW_SECONDS`, and `:481` introduces `FF_MFA_STEP_UP`. ### 2. `elevation_required` is only signalled via the `message` string

`src/modules/auth/routes/guards/elevation.guard.ts:75`:

```ts
throw new ForbiddenException(ELEVATION_REQUIRED_ERROR);
```

That produces `{ statusCode: 403, message: 'elevation_required', error: 'Forbidden' }`. Clients therefore have to substring‑match on `message` to distinguish this from any other 403 (guard fails, permission denied, etc.). Any future global exception filter that reshapes the body would silently break the client contract. Prefer a dedicated code field, e.g. `throw new ForbiddenException({ code: 'elevation_required', message: ELEVATION_REQUIRED_ERROR })`, and pin that shape in the e2e (`elevation.integration.spec.ts` currently asserts on `body.message`).

Works today because Nest's `@UseGuards` extends the metadata array, but the ordering across multiple decorators is not something a reader can just read off the file — it's the only route in the changed set that does this. Every other gated route in this PR uses a single `@UseGuards(AuthGuard, ElevationGuard, ...)`. Consolidating matches the rest of the diff and eliminates the "which one wins?" question:
