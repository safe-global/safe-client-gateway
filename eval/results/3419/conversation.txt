Thanks. 1 and 2 were straight fixes; 3 I'd like to push back on.

**1 — Abuse controls on unauthenticated endpoints.** Fixed in 70e6cb61. Added `TokensRateLimitGuard` under `src/modules/tokens/routes/guards/`, a `RateLimitGuard` subclass reading `tokens.rateLimit.max` / `tokens.rateLimit.windowSeconds`, declared with `@UseGuards` at the controller level so both routes share one budget. Defaults are 60 requests per 60 seconds from `TOKENS_RATE_LIMIT_MAX` / `TOKENS_RATE_LIMIT_WINDOW_SECONDS`, declared in `RootConfigurationSchema` with `.min(1)` so a zero budget fails at boot instead of rejecting every caller, mirrored in the test config and documented in `.env.sample.json`. Two integration tests cover the 429.

One thing that turned up while doing it: these are the first rate-limit variables declared in `RootConfigurationSchema`. The existing `AUTH_RATE_LIMIT_*` and `SPACES_*_RATE_LIMIT_*` are mapped in `configuration.ts` but never declared there, so a malformed value on any of them is a runtime surprise rather than a boot failure. Out of scope here, raising it as a separate gap against non-negotiable 7.

**2 — ValidationPipe everywhere.** Fixed in the same commit. Both `chainId` params now pipe `ChainIdSchema`.

**3 — Batch and chunk upstream calls.** Not changed. I don't think the rule reaches this constant, for three reasons.

The rule governs chunk size: splitting one large input across several upstream calls to respect a provider's documented per-request limit. None of that exists on this path. The Transaction Service has no batch token endpoint, so there is nothing to chunk. Each upstream call carries exactly one address, and `MAX_TOKEN_ADDRESSES` is an input cap at the route boundary that rejects with 422. It does bound the fan-out, which is the concern behind the rule's `why` (the unbounded batch in PR `2532`), and that concern is already satisfied by the cap existing.

Making it config-driven would put a number that is part of the published API contract behind an environment variable. It is interpolated into three Swagger descriptions and reaches the generated wallet-monorepo client verbatim, in `packages/store/src/gateway/AUTO_GENERATED/tokens.ts`, whose CI check compares a sha256 of the entire staging spec. An ops-side tweak to the variable would then turn a check red in a different repo with no code change on either side, and the spec would advertise a bound that another deployment does not honour.

The rule's own canonical example is not config-driven either: `CoingeckoApi.MAX_BATCH_SIZE` is a `private static readonly` literal.

What I did take from the finding: 20 is coupled to the rate-limit budget, the two multiply into the worst-case upstream fan-out per caller per window, and nothing in the code said so. f1679bbd records that coupling on the constant and points at the rate limit as the knob to turn, since that one is config-driven and is not part of the contract.

If you'd rather follow the rule literally I'll add the config value; in that case I'd also drop the number from the Swagger descriptions, so the published spec stops varying with the environment.
