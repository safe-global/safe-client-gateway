#### 1. Wasted DB round-trip on the never-subscribed path

`src/modules/billing/routes/billing.service.ts:194-199`

```ts
const [spaceCreatedAt, hasEverSubscribed, activePlanName] =
  await Promise.all([
    this.spacesRepository.findCreatedAtById(spaceId),

    this.subscriptionsRepository.getActivePlanName(spaceId),

```

`isOfferedToSpace` only reads `activePlanName` when `hasEverSubscribed === true`, so for every never-subscribed workspace (the vast majority pre-enforcement) `getActivePlanName` fires a `SELECT` whose result is discarded. Either fold both into a single `subscription` query (one SELECT returning `exists` + `planName`), or resolve `activePlanName` conditionally.

#### 2. Checkout path now re-runs the full offer computation

`src/modules/billing/routes/billing.service.ts:125`

Every `POST /checkout-url` call now does: general catalog fetch + space-specific catalog fetch + 3 DB queries + the actual checkout POST. The upstream catalog reads are cached (good), but the three DB queries fire on every checkout attempt. If checkout is a hot enough path, consider a lighter-weight `assertOffered(paymentLinkId, spaceId)` that reuses cached catalogs and short-circuits DB reads.

Not a blocker — the safety property (filtered list must match checkout) is worth the cost — but worth noting.

---

#### 3. `warnOnUnclassifiedTrials` will spam on every request

`src/modules/billing/routes/billing.service.ts:163,179-189`

The warn fires on **every** call to `listOfferedPaymentLinks`, which means every `GET /payment-links` and every `POST /checkout-url` for the same misconfigured catalog. In a bad configuration this can flood logs with the same message every request. Consider either:
- logging at `debug`/rate-limited `warn` per link id (dedup via an in-memory Set for the process lifetime), or
- moving the check to a catalog-refresh path (only warn when the datasource actually re-fetches).

Same rationale the PR body cites ("look loudly instead of silently") still applies, just once rather than N times a minute.

---

#### 4. Style: `switch (true)` in `payment-link-offer.rules.ts:53`

The four-arm `switch (true)` is unusual for this repo — a plain `if / else if` chain reads a bit more naturally and is easier to `git blame`. Purely a style call.

---

#### 5. Redundant `hasAnySubscription` when `getActivePlanName` covers the "on a plan" case

`src/modules/entitlements/domain/subscriptions.repository.ts:44-73`

Two very similar methods that always fire together. `getActivePlanName` already resolves whether an active subscription exists (non-null return); `hasAnySubscription` only adds coverage for terminal/incomplete rows. A single query returning `{ activePlanName, hasAnySubscription }` would halve round-trips and remove a code path that's hard to keep in sync. Feels like unnecessary API surface today.

#### 6. Minor: `parseEnforcementStartsAt` semantics

`src/config/entities/configuration.ts:1073-1079`

`new Date(envValue ?? '2099-01-01T00:00:00Z')` treats an **empty string** as "invalid → throw" but **unset** as "use default". That's the tested behavior, but it's slightly surprising for operators who set `ENTITLEMENTS_ENFORCEMENT_STARTS_AT=` in a `.env` file. Consider treating empty-string as unset (`envValue?.trim() || undefined`) for consistency with other keys in this file.
