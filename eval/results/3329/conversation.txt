Not worth blocking on (matches how the other guard handler was written), but if you're touching this again, extracting a shared `handleGuardLike(chainId, dataDecoded, SetCls, DeleteCls)` would remove ~20 lines and one future drift risk. [Fix this →](https://claude.ai/code?q=In%20src%2Fmodules%2Ftransactions%2Froutes%2Fmappers%2Fcommon%2Fsettings-change.mapper.ts%20on%20branch%20tongyao%2Fwa-2921-cgw-recognise-150-as-a-known-trusted-version%2C%20refactor%20handleSetGuard%20and%20handleSetModuleGuard%20into%20a%20shared%20private%20helper%20that%20takes%20the%20Set-%20and%20Delete-%20entity%20constructors%2C%20since%20the%20two%20methods%20are%20otherwise%20identical.&repo=safe-global/safe-client-gateway)

**2. Missing negative-path test for the `MULTICHAIN_SUPPORTED_VERSIONS` change** — `src/modules/safe-shield/recipient-analysis/recipient-analysis.service.spec.ts:1695`. The added test confirms a 1.5.0 Safe → chain-with-1.5.0-deployments yields `MISSING_OWNERSHIP`. There's no complementary test asserting that a 1.5.0 Safe → chain **without** 1.5.0 deployments still returns `INCOMPATIBLE_SAFE`. Since the whole reason for adding `'1.5.0'` to that list is that `checkVersionCompatibility` gates it per-chain, a regression there (e.g., a future refactor short-circuiting to `true`) would silently mark 1.5.0 as compatible everywhere. One extra test on a chain with only 1.4.1 deployments would lock this in.

**3. `.yarnrc.yml` — `npmPreapprovedPackages: ['@safe-global/*']` bypasses the 7-day age gate** — worth being explicit: any package published under `@safe-global/*` now skips the cooling-off window that hardened-mode adds. If an `@safe-global` npm publish token were ever compromised, a malicious version would land in CI/prod immediately instead of after a week. The trade-off is fine for in-house packages (and matches safe-wallet-monorepo), but the scope is broad — narrowing to specific packages you actually consume, or at least documenting the threat model, would be safer than a wildcard.

**4. Nit — `NULL_ADDRESS` string comparison** — `handleSetModuleGuard` compares a decoded string to `NULL_ADDRESS` (all-lowercase) with strict `!==`. The zero address has no checksum bits, so this is safe in practice, but it inherits the same fragility as `handleSetGuard`: if the decoder ever normalized to checksummed form on non-zero addresses, this exact comparison would still be fine, but a lowercase-vs-uppercase mismatch elsewhere would break. Non-actionable for this PR — flagging only because the pattern is now duplicated.

#### Not concerns
- Entity shape mirrors `SetGuard`/`DeleteGuard` exactly; OpenAPI registration + `SETTINGS_CHANGE_METHODS` list are all in sync.
- `MULTICHAIN_SUPPORTED_VERSIONS` ordering (1.5.0 first) is fine — it's a `.some()` short-circuit, not a priority list.
- Deployment-fixture updates in `deployments.helper.spec.ts` are pure data changes tracking the `safe-deployments` bump.
